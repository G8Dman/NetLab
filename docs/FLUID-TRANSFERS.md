# Передача жидкостей — NetLab Automation 0.5.0

Мультиинтерфейс передаёт жидкости через NeoForge FluidHandler выбранной стороны соседнего блока. Работают баки и машины модов, которые предоставляют эту capability, а также обычные котлы NeoForge. Никакой отдельный мод-библиотека не требуется. Ведро, лежащее в сундуке, остаётся предметом: жидкости читаются из баков блока, не из предметов его инвентаря.

Настройка та же: сервер автоматики с IP и паролем; мультиинтерфейсы подключены Ethernet к сети, имеют разные IP, server-address IP_СЕРВЕРА, target СТОРОНА. У источника permission extract on, у получателя permission insert on. Между разными подсетями нужны маршруты и шлюзы с обратной доставкой. В одной подсети шлюз не обязателен.

В приложении ПК/ноутбука:
1. «Интерфейсы» → выбери устройство → переключатель «Предметы / Баки». Видны имя жидкости, объём, вместимость и доступность слива; пустые баки можно скрыть.
2. «Отправить» → кнопка «Предметы / Жидкости» рядом с «Обновить» → режим «Жидкости».
3. Выбери источник, жидкость из сетевого опроса, получателя и объём в mB. 1000 mB = одно ведро. Одна операция: 1..16000 mB.
4. Нажми «Отправить». Как и с предметами, после доставки предложения есть окно 20 секунд, затем идёт пакет жидкости и заполнение получателя. Статус и остаток — в «Заданиях».

Через Console именно сервера после enable:
inspect 192.168.1.11
transfer-fluid 192.168.1.11 192.168.1.12 minecraft:water 1000
show jobs

Адреса — пример, используй свои. Настройка мультиинтерфейсов остаётся в их Console. В общей FluidHandler API нет команды «слить/заполнить конкретный бак по номеру»: распределение по совместимым бакам выбирает сам блок. Выбор жидкости сохраняет её компоненты; несовместимые разновидности не смешиваются.

Жидкость физически сливается в серверный журнал и хранится там до реальной сетевой доставки. При полном баке получателя остаток не пропадает: его можно доставить позднее или вернуть через «Задания». claim БИЛЕТ IP и return БИЛЕТ работают и для жидкостей. Журнал хранится отдельно от карты памяти, как прежние предметные грузы.

Открытый OFFER можно перехватить анализатором и погасить билет на свой принимающий интерфейс. Зашифрованный роутерным VPN пакет не раскрывает билет, тип жидкости и объём. В очках жидкостный груз выделен синим и значком ведра; на защищённом участке содержимое скрыто. Передача использует общий планировщик сети, задержки, VLAN, маршруты и настройки скорости.

Для пробы без сторонних модов поставь два котла, источник заполни полным ведром воды или лавы, получатель оставь пустым. Подключи по мультиинтерфейсу к каждому. Запроси 1000 mB: обычные котлы принимают и отдают только объёмы, которые допускает их FluidHandler; частично наполненный водой котёл может не разрешать слив. Озеро, водяной блок и ведро в сундуке не являются жидкостным баком.

Эта версия добавляет ручную отправку жидкости и просмотр баков. Правила «Логики» и шаблоны крафта пока работают с предметами. Права стороны и запреты машины не обходятся. Если внешний адаптер нарушает контракт или выбрасывает исключение после изменения бака, передача блокируется для ручной сверки, автоматическая повторная выдача не выполняется.

## Проверка

Сборка проверена без запуска Minecraft. Проверки используют настоящие FluidTank/FluidStack NeoForge и кодеки NBT: чтение без расхода, слив, частичное заполнение, сохранение остатка, отказ смешивания воды/лавы и компонентов одной жидкости, повторное погашение билета, совместимость прежнего журнала предметов. Сетевой тест проводит манифест по линии источник → коммутатор → получатель и выдаёт жидкость только на рассчитанном сроке доставки. Проверены объёмы в trace и скрытие содержимого VPN. Клиент, сервер, мир и GameTest не создавались; игровой интерфейс и котлы в живом мире требуют ручной проверки.

Результаты проверки: `./dev.sh build` — 7145 проверок чистой модели; standalone `FluidRuntimeCheck` — 488 прежних проверок реестров/меню/конфигурации, 326 мобильных и 30 жидкостных сценариев.
