# Приложение автоматизации и память — NetLab 0.14 / Automation 0.4

Automation 0.4.4: «Логика» → «Предмет» → первый пункт «Любой предмет».
Это выгрузка источника, без проверки запаса получателя. Слот источника задаёт
точную ячейку, -1 разрешает первый доступный непустой слот. Партия 1–64
ограничивает одну отправку; после её завершения правило продолжает выгрузку.
Сетевой снимок передаёт количество, доступное для пробного извлечения; закрытые
стороны/слоты и permission extract off не обходятся. Передача использует
конкретный item ID и выбранный слот, проверяет их снова при извлечении,
проходит обычные escrow/OFFER/ITEM_DATA/VPN. Маркер * хранится только в правиле.
В ручной отправке и рецептах «Любой предмет» не предлагается. Выбор предмета
логического правила отделён от выбора результата рецепта/ручной передачи.

NetLab 0.14.2 / Automation 0.4.3: портативный терминал явно фиксирует состояние
устройства после команды, после асинхронного завершения и при закрытии.
Хук ConsoleExtensions.flush сохраняет также производные настройки дополнения.
История, token и режим Console остаются временными; новое подключение требует
снова enable. Карта по-прежнему нужна для переживания перезагрузки устройства,
а её отсутствие не сбрасывает работающую конфигурацию при закрытии терминала.

Логин запоминает до 16 успешных IP в личных данных игрока с сохранением после
выхода и возрождения. Список не включает пароли; выбор/изменение IP очищает поле
пароля. Существовавшие до обновления подключения задним числом не восстанавливаются.

Интерфейсы открываются сеткой: номер, иконка, количество. Фильтр пустых сохраняет
исходную нумерацию; выбор непустой ячейки переносит предмет/слот в форму отправки.
В остальных вкладках есть списки устройств, предметов, правил, шаблонов и заданий.
В рецептах выбор ингредиентов идёт из реестра предметов с поиском; эта форма
задаёт план и не извлекает предметы. Рецепт проверяет сервер, а отгрузка требует
настоящего запаса. Правило из списка заполняет форму для нового правила; рецепт
при сохранении с тем же именем обновляется. Ручные IP и ввод билета сохранены.

Пакеты предметов и их время в очках с 0.14.1 / 0.4.2: [ITEM-PACKETS.md](ITEM-PACKETS.md).

Automation 0.4.1: вкладка «Отправить» выбирает источник из выпадающего списка
«имя интерфейса | IP». После выбора по сети запрашивается снимок инвентаря;
открывается список непустых слотов с иконками, локализованными названиями,
количеством и номерами слотов. Переименованные предметы сохраняют своё имя.
Выбор предмета задаёт его ID и точный слот; количество ограничивается доступным
в выбранном слоте и 64. Слоты можно уточнить вручную (-1 означает любой).
В списках есть поиск, колесо прокрутки, стрелки, Enter и Esc для закрытия списка.
Страницы LAN доступны внизу списка устройств. Для получателя тоже есть список
по имени/IP, при этом адрес за шлюзом по-прежнему вводится вручную.
«Обновить содержимое» повторяет сетевой опрос. Это снимок, а не постоянная
подписка на содержимое сундука; передача проверяет актуальное состояние на сервере.

PC/Laptop: CISCO-AUTOMATION в новом app0 [APP], без дополнительных Ethernet
портов. Wi-Fi и USB-RS232 не занимают этот слот. Приложение регистрируется
дополнением через client DesktopApps. Сервер проверяет наличие модуля, питание,
расстояние до ПК, идентичности, эпохи, пароль и локальную подсеть для каждого
действия, включая асинхронные продолжения и отмену при logout.

Сервер: configure terminal → management password PASSWORD (8..64 без пробелов).
GUI получает случайный сеанс, привязанный к игроку/ПК/серверу/верификатору пароля.
PBKDF2-HMAC-SHA256, 60 000 итераций, соль 16 байт. Вход ограничен своей подсетью
без роутера; actual TCP 5420 должен пройти в обе стороны. Запросы и ответы GUI
передаются ApplicationTransport, большие ответы — последовательными частями.
Управление интерфейсами (IP/target/manager/права) по-прежнему требует Console.

Каталог опрашивает локальные управляемые узлы по сети, по 16 на страницу;
инвентарь выбранного узла читается отдельным SNAPSHOT. До 256 слотов на снимок.
Правила stock поддерживают точные слоты или -1, минимум и партию до 64. На сервер
до 16 новых правил и 16 шаблонов. Старые CLI-правила продолжают работать.
Кнопки запуска/остановки не требуют держать ПК открытым.

Crafting-table adapter: реальные входы 0..8 и выход 9 в CraftingGrids SavedData.
RecipeManager определяет разрешённый crafting-рецепт и проверяет результат.
Сжатая сетка CraftingInput.Positioned отображается обратно в исходные слоты.
План расхода/возвратных предметов/выхода проверяется целиком до мутации.
При поломке интерфейса его сетка выпадает. Обычный верстак не получает скрытого
ванильного контейнера: это инвентарь адаптера, доступный через мультиинтерфейс.
Реальные ItemStacks не входят в память конфигурации.

Шаблон: один исходный склад, один интерфейс верстака, адрес получателя, желаемый
запас результата и девять item IDs (пустая ячейка '-'). Компоненты NBT в редакторе
не задаются. Поддерживаются стандартные/модовые CraftingRecipe, не специальные
процессы произвольных машин. Производственные цепочки строятся через промежуточные
интерфейсы; рекурсивного глобального планировщика AE2 нет. Каждый этап доставки
сохраняет OFFER-окно 20 секунд. Одна незавершённая передача блокирует новые этапы
этого сервера, предотвращая повторные заказы до подтверждения.

Публичный приём: receiver public/private в Console endpoint. Каталог возвращает
IP/UUID/ник через сетевой запрос. GUI рисует голову по UUID (fallback default skin).
Публичность разрешает только вставку; источник всегда должен доверять своему
серверу и принадлежать его владельцу. Обычный journal/Claim применяется и к
межигровой отправке. Открытый билет можно украсть, AES-GCM выполняют роутеры;
исходная/конечная LAN остаются открытыми. Вход GUI — учебный незашифрованный
локальный запрос. Нельзя обещать VPN-защиту от SPAN внутри своей LAN.

TransferJournal добавляет ограниченную SHA-256 цепочку (4096 событий с якорем).
Это аудит централизованного escrow, не распределённый консенсус или защита от
редактирования/отката сохранения администратором. Незагруженные узлы удерживают
груз в журнале; постоянная замена исходного физического endpoint не восстанавливает
его identity по карте, и штатная выдача такого билета остаётся остановленной.

MemoryCards: на новых конфигурируемых устройствах данные без карты временные.
Старые сохранения/настроенные предметы мигрируют на активную карту. Пустая карта
активируется и далее автоматически сохраняет настройки. Записанная карта требует
memory read/кнопки чтения; memory write активирует перезапись текущей конфигурацией.
Карта вставляется/снимается на выключенном устройстве, через вкладку «Память».
Тип, шасси и установленные аппаратные модули должны совпадать. Физические модули,
владелец и идентичность не клонируются. Router VPN credentials зеркалируются с
VpnStore и восстанавливаются при чтении; разрешения LAN/VLAN проверяются живой
TrafficAuthority и не обходят отзыв/регистрацию сети.

PC/Laptop сохраняют конфигурацию в выпавшем настроенном блоке; в creative
playerWillDestroy выдаёт такой блок. Терминальные транскрипты не переносятся:
разрыв Console продолжает очищать прежнюю историю. Объекты карты и настроенной
техники используют persistent configuration component с пустым wire codec,
а block entity update tag редактирует секреты. Большой Device JSON сохраняется
StoredJson-частями. Настройки сервера включают пароль/stock rules/patterns;
инвентари, журнал и глобальная регистрация LAN хранятся отдельно от карты.
